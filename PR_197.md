Fixes every finding of the cross review in #197 -- all 16, plus the two filed as minor -- with a regression test for each in `tests/test_crossreview_197.py`, and carries the work that followed from it. Suite: **2143 passed, 2 skipped, 0 failed** (the review's run had 1 failing, F10).

What the critical six had in common is worth stating: each returned a plausible wrong answer with no error at all.

### Silently wrong results

- **F1** `noise=` was honoured by `run()` and by nothing else. `shots()`, `statevector()`, `oneshot()` and `probs()` each grabbed the default backend and passed the argument to something that did not know it. Backend selection now happens in one place all of them use; `probs()` reads the density matrix's diagonal, and `statevector()`/`oneshot()` raise, because a noisy state has no statevector and returning the noiseless one is worse than an error.
- **F2** A measurement with no key was skipped by the fast path, so a circuit using that qubit afterwards reported a value drawn from the final state instead of the one measured — and adding a key to the same circuit changed the distribution. Collapse now triggers on a measured qubit being used again, as target or control; terminal measurements keep the fast path.
- **F3** The same defect in the density backend, which recorded no classical bit at all. It now collapses and records when a measurement is non-terminal. The returned density matrix is unchanged: averaging over an unread measurement is dephasing, which it already did.
- **F4/F5** The QASM parser dropped `qreg` widths, so declared-but-idle qubits vanished and a `to_qasm`/`from_qasm` round trip shrank a circuit; and `h q;` over a whole register parsed to an empty target list, was appended, and did nothing.
- **F6** `calc_u_params` read two phases off matrix entries that are zero for an antidiagonal unitary, where `cmath.phase(0)` returns `0.0` silently. X and Y reconstructed as *different gates*, not a different global phase, and the one-qubit decomposers emitted non-equivalent circuits. 2000 random antidiagonal unitaries now round-trip.

### Crashes and exposure

- **F7** The 2q transpiler called `.fallback()` on anything it could not decompose, but most two-qubit gates are not `IFallbackOperation`: 13 of 18 died with a bare `AttributeError`.
- **F8** The composer backend built a `set()` from `op.targets`, which is not iterable when it is a slice, so `h[:]` always raised.
- **F9** The angle parser avoids `eval` but allowed unbounded `**`, and reads text arriving from MCP clients. Exponents are capped.
- **F10** The API key file was chmod-ed after being written. It is now created with `0o600`, and on Windows says plainly that it cannot be made owner-only.

### Inconsistencies

**F11** return type of `returns='shots'`; **F12** the >28-qubit statevector guard skipped when `shots=` was given; **F13** `ancilla(pos=-1)` landing on a data qubit that the block's reset then erased; **F14** `QaoaAnsatz` ignoring a mixer's width; **F15** `2q_decomposition` uncallable through `run()`; **F16** `iswap`/`zz` and their daggers refused by the stabilizer backend as "not Clifford" when they are. The F16 fix also takes the rewrite dispatch's arity from the gate class rather than a hardcoded list of names, which is what would have made the next addition fail the same way.

### Beyond the review

Reported separately by the `blueqatmcp` session and included here:

- **Mid-circuit measurement could not be exported.** Every measurement was written to `measure q[i] -> c[i];`, so a circuit that reuses a qubit lost its earlier value, and `m(key=...)` changed nothing in the output although `Circuit.run()` distinguishes the results. Keys now name classical bits, re-measurements get their own, and `creg` is sized to fit. **Circuits measuring each qubit at most once emit byte-for-byte what they always did**, pinned by an exact-string test — the hosted service submits `to_qasm` output directly to hardware.
- The bundled MCP server's tools are renamed to say they take QASM (`run_qasm`, `qasm_stats`, `qasm_expectation`, `draw_qasm`, `qasm_to_eo_pulses`, `run_qasm_on_cloud`). blueqat's hosted service exposes tools for the same jobs taking a JSON gate list, and under bare names a client with both registered cannot tell which it is calling. The Python functions keep their names, so importing the module is unaffected.
- Docs gain the route in from another toolchain — transpile to `u`/`cx` elsewhere, import as QASM — verified on a real circuit: a Qiskit-transpiled MPS sequential-generation program, 4 qubits and 8 CX, reproduces the exact Born distribution to a total variation of 0.0011 over 200000 shots.

### Turning matrices into circuits

That last item is a workaround, and the reason it was needed was that blueqat could not decompose an arbitrary unitary at all. `blueqat/decompose.py` now does:

- `decompose_two_qubit` — exact, via the Cartan (KAK) factorization. `basis='rotations'` emits `rxx`/`ryy`/`rzz` (six CX compiled); `basis='cx'` emits CX directly and needs **four**, because CX conjugation turns an `rx` on one wire into an XX term and an `rz` on the other into a ZZ term, so one sandwich carries both. The three terms commute, so they split into (XX, ZZ) and (YY), and conjugating the XX sandwich by `s` supplies the YY. Degenerate interactions cost less without being special-cased: `cx`, `cz` and `zz` are two CX, the identity none.
- `synthesize_two_qubit` — the optimal three CX, by fitting rather than solving. It is checked, not assumed: below `tol` infidelity or it raises. Worth knowing what that bounds, and now documented: an infidelity, not the matrix. Amplitudes land about `1e-7` from the target and tightening `tol` to `1e-14` only reaches `1e-8`, which is why the exact four-CX route exists.
- `decompose_unitary` (Quantum Shannon) and `decompose_isometry` for any width. `basis='cx'` compounds there: 36 CX to 28 at three qubits, 168 to 136 at four.

The two-qubit construction was searched for in blueqat's own gate conventions rather than taken from a remembered template — two earlier guesses were wrong — and the sandwich identity reproduces `exp(i(a XX + c ZZ))` to `1.2e-16`.

### The path taken without SciPy

SciPy is not a declared dependency, so `cosine_sine` carries a fallback. Every test run on a machine that has SciPy took the other path, so the fallback was never executed; blocking the import showed three failures, including Toffoli and Fredkin. The cause was a threshold: `sines` came from `sqrt(1 - cosines**2)`, and at `cosines == 1` that cancels to machine epsilon while the square root lifts it to ~`1.5e-8`, clearing a `1e-9` "is this column determined" test and dividing by its own noise. Unitarity makes the column norms the sines exactly, so they are taken from there. Tests now run the fallback explicitly, and the suite passes both with SciPy and with it made unimportable.

### Cloud: telling an unknown outcome from a failure

A Cloudflare 524 fires after ~100 seconds of *silence* from the origin — a bound on how long a reply may take to start, not how long the work may take. Collapsing it into `Blueqat cloud error 524` told the caller the opposite, and the natural response, resubmitting, spends another hardware slot and more money on work that very likely already ran. Gateway timeouts and socket timeouts now raise `CloudOutcomeUnknown` (a `RuntimeError` subclass, so existing handlers still work); a refused connection stays a plain failure. The warning is only actionable with a way to check, and there was none — `submit_hardware_job` was the last word on a job — so the endpoints the service already publishes are exposed: `hardware_jobs`, `hardware_job`, `hardware_job_result`, `cancel_hardware_job`, `hardware_quote`, `hardware_next_window`, `hardware_calibration`. Paths and payloads come from the live schema, not from guesswork.

A 403 gets the same treatment, for the same reason. The service sits behind Cloudflare, which refuses the `Python-urllib` User-Agent *before the request reaches the service* -- so the key was never seen, and the one reading a bare 403 invites is the wrong one. Such a 403 now says so. Both of Cloudflare's body shapes are handled, since it content-negotiates its own errors and this client always asks for JSON. Measured one variable at a time against the live endpoint: no header is 403 because urllib supplies that signature itself, an empty agent is 200, a one-character agent is 200 -- the rule is about that string, not a missing header.

The request headers themselves were unpinned until now: every cloud test goes through a fake transport, so nothing ever built a real request. Dropping the User-Agent in a tidy-up would have broken every live call while the suite stayed green, and the failure would have read as "the service is down".
